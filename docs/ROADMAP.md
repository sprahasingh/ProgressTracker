# ProgressTracker roadmap

This roadmap describes the adaptive productivity and goal-tracking direction while keeping existing local records and the already deployed Supabase schema intact. Each implementation step should be separately reviewable, tested, and documented.

## Repository audit

- Today provides current-day local check-ins; Overview, History, Goals, Analytics, and Achievements show workspace-local progress. The Goals route includes an interactive cumulative allocation planner.
- Dexie v3 stores legacy categories/daily entries alongside the generic tracker/entry tables; journals, legacy goals, metrics, progress snapshots, settings, and pending operations remain in their original stores.
- `localRepository.ts` wraps local reads and writes. UI code should continue to use repositories rather than reach into Dexie directly.
- Supabase has the seven legacy user-owned tables plus forward-only generic `trackers` and `tracker_entries` tables, each protected by RLS. The original migration is treated as applied history and must not be edited as a schema redesign mechanism.
- Supabase magic-link authentication is present. Password authentication and synchronization are not part of the generic domain step.

## Architecture boundaries

- `src/domain/trackers` owns transport- and storage-independent tracker definitions, schedule shapes, metrics, qualification rules, custom fields, milestones, entry values, planning, streaks, and derived rewards.
- Zod schemas validate persisted/imported/API-shaped values at boundaries. Evaluation/planning are pure domain operations; the setup editor validates all configured nested values before persistence.
- `src/db` remains the IndexedDB adapter. Dexie v4 keeps the original database as the guest workspace and uses per-user database names for authenticated workspaces. Guest import is explicit, transactional, verified, and non-destructive.
- Future cloud persistence requires additive, forward-only migrations and RLS/pgTAP coverage. Keep sync transport out of components and do not treat client timestamps as trusted concurrency data.

## Stages

1. **Generic domain foundation** — completed: versioned generic tracker/entry types, validation schemas, and non-destructive projections from legacy categories and daily entries.
2. **Pure domain behavior** — completed: deterministic achievement classification, nested AND/OR/at-least rule evaluation, rest-day-aware workload distribution, recalculation, and deadline state results. Timezone-aware schedules and richer recurrence semantics remain documented limitations.
3. **IndexedDB evolution** — completed in this phase: Dexie v3 generic tracker/entry tables and a transactional projection of legacy categories/entries, verified from v1/v2 fixtures and after reopen. Original legacy rows remain intact.
4. **Cloud schema evolution** — implemented as additive migrations and pgTAP coverage for generic tracker ownership, cross-user references, tombstones, revisions, and planner schema v2. Owner reports hosted migrations `20261008000100`, `20261009000100`, `20261009000200`, and `20261009000300` are applied and migration history is reconciled; no hosted database access was performed in this turn.
5. **Tracker setup flows** — implemented in this phase: local tracker list/create/edit/archive with schedule and date setup, first metrics, type-aware defaults, and Zod validation.
6. **Metrics and rules editor** — completed in this phase: editable multi-metric definitions, numeric/duration/checklist measures, directional thresholds, streak qualification, nested AND/OR/at-least rules, typed custom fields, and metric-linked milestones.
7. **Daily logging and adaptive schedules** — completed: Today filters by deterministic schedule occurrences, captures configured metric/custom-field values, supports skip/update/clear, persists local tombstones, and explains configured rule qualification. Account workspaces enqueue generic tracker and entry changes for account-scoped sync; sync runs after account workspace activation, browser reconnection, and committed account tracker/entry edits, and also remains manually available.
8. **Challenges and rewards** — completed: pure streak summaries count qualifying scheduled occurrences, treat rest days as neutral, keep the current day open until explicitly logged or elapsed, and preserve personal-best streak rewards after missed opportunities. Default points and milestones are deterministic and derived from retained entries; the Achievements screen presents them without adding reward-ledger persistence.
9. **Dashboard and history** — completed: Overview summarizes active trackers, recent success/consistency, derived rewards, current-month calendar activity, and per-tracker streak/latest-value progress; History filters real entries by tracker and 7/30/90-day range. No sample activity, edits, or cloud reads are introduced.
10. **Quality pass** — code-level pass completed: keyboard skip-to-content and route navigation, semantic calendar table, field labels/status messages, retry and empty states, responsive CSS breakpoint review, and connected Today → Overview → History test coverage. Manual real-browser viewport and screen-reader verification remains.
11. **Authentication expansion** — completed: retain magic-link sign-in and add email/password sign-up/sign-in, neutral password-reset requests, recovery-session password update, and password setup/change for signed-in magic-link users. UI and service behavior are covered by mocked tests; hosted inbox delivery/configuration remains owner-verified.
12. **Offline/cloud sync** — phased. **12a local account isolation (completed):** preserve guest data, create per-user IndexedDB workspaces, offer an explicit guest import/separate choice, and isolate rendered state on account switches. **12b server write boundary (implemented and locally pgTAP-verified):** account-bound RPC, expected-revision checks, idempotent receipts, and cross-owner protection. **12c client outbox/pull engine (implemented):** account-bound queued writes, revision metadata, full keyset pulls, tombstone propagation, retry retention, and conflict records; never merge rows whose owner differs, hold child uploads until tracker parents are safely written, and preserve newer local edits made during an in-flight upload. **12d recovery UX (implemented):** account-scoped conflict comparison and explicit keep-local/use-cloud decisions with revision-aware retries. **12e collision recovery (implemented):** fork an unreadable local tracker ID while relinking local history; fork unreadable entry IDs; preserve same-day cloud identity when resolving duplicate entries; and discard obsolete child conflict snapshots when their parent is forked so fresh server results drive any retry conflict. **12f workspace rendering guards (implemented):** wait for Supabase's initial session event, require the active workspace owner to match auth state before rendering routes, and discard tracker-list reads that finish after a workspace switch. **12g guest import collision handling (implemented):** users can abort on an ID collision or explicitly import colliding data under new IDs with parent links remapped; source reads use one IndexedDB snapshot transaction, decisions are idempotent under concurrent retries, and source rows remain intact. **12h hosted migration preflight (prepared):** read-only SQL catalog checks for the hosted project's generic tables, RLS, RPC grants, and receipt privacy. **12i safe automatic sync triggers (implemented):** one account-scoped attempt after the authenticated workspace is ready and after an offline-to-online transition. **12j edit-triggered synchronization (implemented locally):** committed account-owned tracker/entry writes, archive changes, tombstones, and conflict choices that queue local changes publish a user-scoped event; the provider debounces rapid saves, waits for an in-flight attempt before checking for newer edits, and only syncs when that same account workspace is ready and online. Guest changes never publish. Errors keep the outbox and do not start retry loops; reconnect and manual sync remain retry paths. No polling or automatic guest import is enabled. Hosted behavior was not re-executed in this phase.
13. **Workspace backup and restore** — implemented locally: the Account page offers a versioned JSON download and an explicit preview/restore flow for the matching guest or account workspace. Validation checks the format, owner, record shapes, and sync ownership. Restore is additive, skips exact duplicates, and aborts transactionally on differing ID/date conflicts; it does not overwrite existing rows or directly contact Supabase. Cross-account transfer and app-side encryption are not implemented.
14. **Goals overview and adaptive plans** — completed: the Goals route lists generic goal-kind trackers, derives milestone progress, and visualizes per-metric daily recurring targets or cumulative deadline progress. Daily consistency and missed-day calculations follow the tracker schedule; cumulative values sum only explicitly incremental recorded entries and exclude skipped/tombstoned rows. Planning targets are separate from check-in thresholds. V1 definitions stay v1 until planning is configured; v2 carries planning targets through IndexedDB, backups, outbox, sync, and conflict resolution. Owner reports migration `20261009000300_goal_planning_v2.sql` applied and 119 pgTAP assertions passed across four files. Older clients cannot read v2 definitions.
16. **Interactive Planner Preview (Stage 1)** — implemented: active cumulative-deadline metrics distribute remaining amounts over scheduled dates and accept manual adjustments. Rest days remain visible; actual progress stays separate; shortfall/over-allocation is reported.
17. **Persistent planner allocations (Stage 2)** — implemented locally: schema v3 stores per-metric, per-date allocations and the planning IANA timezone in the generic tracker definition. IndexedDB tracker/outbox updates are atomic; sync and conflict handling reuse the existing account-bound RPC and revision token; backup/restore validates and preserves v3 payloads. The forward-only migration `20261009000400_goal_allocations_v3.sql` allows schema versions 1–3 and has not been applied to hosted Supabase. Production v3 writes remain disabled until the owner confirms hosted migration application and verification. Older clients reject v3 definitions; update devices before saving plans. Local pgTAP execution is pending.
18. **Synchronized Bin and permanent deletion (repair prepared; production gated)** — local tracker tombstones preserve all entries and planning data for a 30-day recovery window; Bin supports restore and explicit permanent-delete confirmation. Account deletion requests remain in an owner-bound IndexedDB queue until server confirmation. The hosted history records `20261010000100_tracker_bin_permanent_deletion.sql`, but the expected objects were reported missing; an earlier `migration repair --status applied --linked` changed history only. The new forward repair `20261011000200_repair_tracker_bin_permanent_deletion.sql` recreates the ledger, idempotent owner-checked deletion RPC, serialized sync protection, and stale tracker/entry/receipt rejection while forcing cleanup off and requiring no `pg_cron` extension. Automatic cleanup is not scheduled by this repair. The verifier accepts absent `pg_cron` while cleanup remains disabled. Do not enable the app flag until repair is applied and verified; configure and verify the scheduler separately before enabling automatic purge. Local PostgreSQL execution and hosted lock-contention/Cron behavior remain unverified.
15. **Workspace analytics** — implemented: the Analytics route summarizes recent check-ins, qualification, schedule consistency, and individual metric observations over 7/30/90-day windows. An unlogged current day remains open. Values retain per-metric units; charts never sum values across dates or combine metrics. Reads are scoped to the currently verified local workspace; no schema or sync changes are needed.
18. **Major UI/UX redesign** — implemented locally: four primary areas (Today, My Space, Insights, Settings) group related routes on desktop and mobile; semantic light/dark colors distinguish action and status; Today includes schedule-aware activity and upcoming deadlines; tracker cards clarify individual targets; and goal/planner and analytics hierarchies are clearer. Goal creation asks for a total, unit, deadline, and estimates pace; habits start with daily check-ins. Post-creation actions offer a first progress/check-in, library view, and customization. Existing goal target semantics and schema versions are preserved. Advanced controls are grouped into focused disclosures. Audit and solution notes are in `docs/UX_REDESIGN_AUDIT.md`. Automated create/edit, card, Today, and navigation tests cover the changed flows; real-device viewport and assistive-technology checks remain manual.
19. **Adaptive numeric precision and clearer goal setup** — implemented locally: goal deadlines appear in the primary creation flow; numeric measures can configure 0–2 decimal places and a permitted increment; planned allocations follow the increment while legacy recorded values stay unchanged; cumulative decimal progress avoids binary floating-point addition artifacts; and help buttons use a single viewport-aware anchored popover. The forward-only migration `20261012000100_tracker_numeric_precision_v4.sql` is prepared but has not been applied to hosted Supabase. Production v4 writes remain off until hosted schema support is applied and verified. Run the new pgTAP file against a local database only after applying the migration there; typecheck, app tests, and build results are reported with this implementation.
19. **Global Holidays & Breaks** — implemented locally: account-wide, date-only holiday rows apply across trackers and goals; a mobile/desktop manager supports inclusive date ranges, reasons, edit, remove, and restore. Calendar status legend uses green complete, orange partial, red missed, and blue holiday markers, with accessible text and saved activity retained on holidays. Streaks and analytics omit holidays as missed/success opportunities; plan pace and allocation recommendations omit those scheduled dates. The additive migration `20261011000100_global_holidays.sql` creates owner-only holiday reads and a revision-checked idempotent RPC write boundary with private receipts. IndexedDB schema v7, account outbox, backups, sync conflicts, and account isolation include holiday rows. The migration has not been applied to hosted Supabase; signed-in cross-device holiday sync must not be considered active until it is applied and verified. Local database tests should run with `supabase migration up` followed by `supabase test db` without resetting the database.

Installable PWA support is implemented locally with a GitHub Pages-scoped manifest, install prompt, and a static app-shell cache. A workspace-local IANA timezone preference now drives current-day and date labels; cloud preference sync and timezone-aware recurrence remain future work. Backup restore cannot transfer data between accounts and does not encrypt the downloaded file.

## Known limitations and risks

- Generic definitions and entries are persisted in IndexedDB. Guest data remains in the original database; every authenticated account has a separate workspace. Account switching gates and unmounts record routes until the correct database is open. Guest import is copied transactionally and the guest source is retained. Sync attempts after workspace activation, reconnection, and committed account tracker/entry edits; rapid edits are debounced and can be manually retried. It requires the account-scoped server RPC migration and does not poll. Legacy records/settings remain outside cloud sync.
- The setup screen supports a compact set of schedules. Rule summaries/preview, reorder controls, checklist progress calculation, and richer conditional custom-field behavior are future refinements.
- The read-only legacy projection maps each old category to a boolean habit with one completion metric. It cannot infer quantitative progress from the free-form note field.
- Category schedules lack an explicit timezone. The current Today screen uses the device's local calendar date; changing travel/account timezone behavior and timezone-aware history/streak semantics remain future work.
- Generic metric and rule schemas are versioned, but future migrations still need explicit conversion rules and compatibility tests.
- Cumulative progress is intentionally per metric; it does not aggregate unlike units. Historical values are treated as snapshots unless the user explicitly opts a metric into incremental semantics, at which point retained historical recorded values count toward the cumulative target. The product does not provide a per-date migration wizard for separating previously cumulative snapshots into increments.
- Generic cloud tables and the account-scoped sync client are implemented. Owner reports that the four local database test files passed 119 pgTAP assertions and that hosted migrations through planner v2 (`20261009000300`) were applied with migration history reconciled. This environment did not rerun pgTAP because its Docker/local database services are unavailable.
- Authentication supports magic links, email/password registration and sign-in, recovery, and setting a password for existing accounts. Hosted Supabase email templates/provider configuration and real inbox delivery require project-owner verification; automated tests mock auth responses and do not perform hosted end-to-end flows.
- Guest import can explicitly fork colliding guest rows and remap relationships; account settings win a settings-row collision while the guest settings remain in the untouched guest workspace. Different daily journals for the same date cannot coexist because each workspace has one journal per date, so that import rolls back and the user keeps the workspaces separate. Existing guest sync-operation records remain in the guest database and are not copied to account queues.
- The Account page can export a versioned JSON snapshot and restore it into the same active workspace. Restore validates records, owner identity, and sync ownership; it adds missing data transactionally, skips identical data, and aborts on collisions instead of overwriting. The app does not encrypt files or support cross-account transfer, so users must keep backups private.
- The installable web app caches only the app shell and same-origin static build assets. Supabase/API responses, auth responses, and user records are not cached by the service worker; productivity records remain in IndexedDB. Browser-specific install prompts and real offline behavior still need manual browser/device verification. The service worker is installed only in production builds, so local development remains unchanged.
- Calendar timezone and appearance preferences are stored per local workspace and do not sync to other devices. Weekly/monthly quota scheduling remains an approximate calendar-date rule; timezone-aware recurrence windows and travel behavior are not implemented.
- Client-side IndexedDB separation protects against accidental cross-account display/upload by the app, but does not protect against access to the same browser profile or developer tools. The client binds queued work to the active account and the server boundary verifies ownership and revisions. The owner reports cross-browser hosted sync and isolation tests passed manually; this environment did not repeat those hosted tests.
- The additive sync write-boundary migration and its 17 pgTAP assertions pass against the local Supabase database. The owner reports hosted cross-browser synchronization, archive, offline reconnection, revision conflict, retry, and account-isolation scenarios passed manually. Automated transport, outbox recovery, in-flight edit retention, parent/child upload ordering, account-scoped conflict choices, collision forking, and account-switch rendering tests are present; this environment has not repeated those hosted manual tests. Forking a tracker relinks its local entries and clears stale child conflict snapshots; the new queued operations are rechecked against the server on the next sync.
- Daily logging creates check-ins for today's scheduled trackers; History can edit an existing check-in on its original date but cannot create arbitrary past-date entries. Goals and Achievements screens present generic goal trackers and derived rewards respectively. Analytics covers recent consistency and metric observations; advanced filtering and tombstone cleanup are not implemented. Weekly/monthly quota prompts use deterministic evenly spaced dates and do not rebalance around missed check-ins.
- Overview shows only the current workspace month and active trackers; History supports 7/30/90-day presets plus a validated custom inclusive date range. History edits are local-first and queue account-owned updates through the existing sync path; archived trackers remain read-only. Calendar-month navigation and cloud-backed legacy history remain future work.
- Responsive layouts have been reviewed in CSS and exercised structurally in jsdom, but not visually in a real browser viewport. Screen-reader behavior has semantic markup and accessible-name tests but still needs manual assistive-technology verification; no browser automation or screen reader is available in the current environment.
- Streak and reward values are derived from available entry history, not stored in a reward ledger. Historical edits/deletions can recalculate earned points and milestones; future sync must define how retroactive changes and account merges affect reward history.
- Planning currently treats dates as date-only values and has a deliberately simple cadence model; monthly/weekly quotas are approximate distribution rules, not a timezone-aware recurrence engine. Daily recurring and cumulative-deadline modes are selectable in goal setup and both show deadline/status information. Missed daily targets do not automatically carry forward; cumulative required pace recalculates over remaining scheduled dates.
- Stage 1 preview allocations are ephemeral and do not survive navigation or reload. Persistent allocations need a versioned definition design, IndexedDB transaction/import/export coverage, cloud migration and write-boundary review, sync conflict policy, and an older-client compatibility plan before implementation.
