# Progression architecture

## Authority and scoring

The progression system treats the database as the authority for permanent XP, levels, and achievements. Trusted database routines append events to the owner-readable `progression_events` ledger after accepted tracker changes. Clients cannot write ledger events or submit XP amounts. Stable award identities, transaction locks, and unique constraints make scoring idempotent. Corrections append reversals; a later qualifying event can create a new award generation.

Current scoring rules are version 2:

- A qualifying saved check-in awards 10 XP.
- A Perfect Day awards 20 XP when one or more trackers are eligible and all eligible trackers have qualifying completed entries. Skips do not count as completions.
- Tracker streak milestones award 35 XP at 7 days, 50 at 14 days, 100 at 30 days, and 200 at 100 days. Existing schedule, holiday, and qualification rules determine eligibility.
- A goal metric milestone awards 25 XP when a saved observation crosses its configured target. Completing a goal tracker awards 100 XP and suppresses its individual milestone awards.

Level thresholds are 0, 100, 300, 600, followed by increments that grow by 50 XP each level. These values and scoring rules are versioned so future changes can be reconciled explicitly.

## Legacy XP and offline activity

Each account is initialized once. When retained server history contains enough evidence to calculate a balance, one `LEGACY_XP_OPENING_BALANCE` event records the estimate for active and archived trackers. The ledger metadata stores the source, calculation version, reconstruction time, and account cutover. The UI labels this **“XP reconstructed from past activity.”** It is an estimate, not an exact reproduction of the former device-calculated total. It creates no individual historic rewards and does not unlock achievements. If no pre-cutover entry history is available or the result cannot fit the ledger, historical XP is `unavailable`; a new account is marked `new_account` and receives no invented zero opening transaction.

The cutover is the account initializer's transaction statement timestamp. Reconstruction includes retained tracker entries whose server-maintained `server_changed_at` precedes that timestamp. Scoring serializes on the same per-account advisory lock. A newly accepted write first initializes the account, then records its award. The initializer marks qualifying entries already present on the cutover calendar day in award state, without creating transactions. This prevents a later same-day edit from adding the same activity again. Perfect Day, streak, and goal rewards use post-cutover activity only. Late uploads dated before the cutover day cannot earn new historical XP; an already active award may still be reversed when its source stops qualifying. This is intentionally conservative because the former authoritative server balance and immutable schedule snapshots were not retained.

Offline estimates are available through the progression data repository as provisional rewards, separate from the confirmed ledger total. They are not ledger awards and do not change official levels or unlock achievements. The repository excludes locally pending entry estimates already represented by confirmed source events. Successful uploads publish a workspace change event so the client can refresh confirmed ledger data without waiting for a download. Permanent write rejections become sync conflicts and stop contributing provisional XP; transient errors remain pending for retry. Consumers should subscribe to progression changes and reload the overview after sync, conflict resolution, or historical correction.

## Reconciliation and history limits

Consistency is the average daily adherence across the latest 30 completed eligible activity days, excluding the open current day and future dates. Daily adherence is completed eligible trackers divided by eligible trackers. The repository returns a null score and no fabricated activity when it has no eligible days. Its local calculation uses currently available schedule and holiday data and starts no earlier than the latest tracker definition update; immutable schedule snapshots are not retained.

A Perfect Day requires at least one eligible tracker and completion of every eligible tracker for that date. Reconciliation must be deterministic and idempotent. Historical eligibility must not be inferred where the required tracker schedule or membership evidence is missing. The current data model does not retain immutable daily snapshots of schedules, holidays, tracker membership, or timezone, so edits to those definitions can affect historical eligibility. Reconciliation therefore avoids unsupported pre-cutover history and dates before the latest known definition change.

Goal rewards use saved observations on goal trackers after account cutover. The system does not infer historical milestone awards from current progress. Tracker deletion anonymizes retained scoring history by removing tracker identifiers and personal metadata while preserving legitimately earned XP. Account deletion cascades progression data with the account.

Persistent achievement progress is derived from authoritative post-cutover scoring state. The achievement catalog stores stable IDs, targets, repeatability, current tier, and the latest qualifying source reference. Unlock and revocation events are append-only and retain generation, timestamp, and source event/date. Corrections can revoke an active unlock; later requalification creates a new generation. Repeatable check-in tiers point to the check-in that crosses each tier. Reconstructed opening XP does not unlock achievements. Achievement tables are owner-readable under RLS, while API roles cannot write progress or history directly. Internal reconciliation functions are not executable by API roles.

## Achievement catalog and calendar rules

There are 14 achievement IDs. The original 12 retain their existing server rules:

| Achievement | Earning condition | Repeatable | Holiday and mode effect |
| --- | --- | --- | --- |
| First Step | One confirmed qualifying check-in after achievement cutover. | No | Standard Mode excludes holidays and unscheduled dates; Strict Mode requires eligibility on holidays and rest days. |
| Momentum | A qualifying streak of 3 eligible opportunities. | No | Standard Mode counts scheduled opportunities and pauses on holidays; Strict Mode counts every date in the tracker period, including holidays and rest days. |
| First Flame | A qualifying streak of 7 eligible opportunities. | No | Same streak rules as Momentum. |
| Steady Flame | A qualifying streak of 14 eligible opportunities. | No | Same streak rules as Momentum. |
| Unstoppable | A qualifying streak of 30 eligible opportunities. | No | Same streak rules as Momentum. |
| Century | A qualifying streak of 100 eligible opportunities. | No | Same streak rules as Momentum. |
| Perfect Day | On one date, at least one tracker is eligible and all eligible trackers qualify. | No (current server) | Existing date-specific schedule rules apply. A Standard holiday is neutral and normally leaves no eligible tracker; Strict Mode still requires completion. |
| Perfect Week | Every required opportunity qualifies in a completed Monday-based week, on at least 3 distinct required dates. | Yes, once per qualifying week | Standard holidays and rest days are neutral; Strict Mode requires active-period dates. |
| Milestone Maker | One confirmed configured goal milestone. | No (current server) | Goal milestones are based on saved goal observations, not daily holiday eligibility. |
| Goal Crusher | One confirmed completed goal tracker. | No (current server) | Completion is goal state, independent of holiday eligibility. |
| Consistency Star | At least 80% average daily adherence across the latest 30 completed eligible dates. | No | Daily adherence is qualifying eligible trackers divided by eligible trackers. Standard Mode excludes holidays and unscheduled dates; Strict Mode treats every in-period date as eligible. |
| Dedicated | First 100 confirmed qualifying check-ins. | No (after `20261105000200`) | Same check-in eligibility as First Step. |
| Perfect Month | A completed month where all required opportunities qualify on at least 12 distinct required dates. | Yes, once per qualifying month | Standard Mode holidays and rest days are neutral; Strict Mode dates are required. |
| The Comeback | After a genuine missed required opportunity, qualify on the next 7 consecutive opportunities for that tracker. | Yes, once per recovery episode | Neutral dates preserve the sequence; saved skips break it but do not trigger it. |

The persisted `repeatable` field in `progression_achievement_progress` is the cadence authority consumed by Wins. Before migration `20261105000200_make_dedicated_one_time.sql`, the server marks Perfect Week, Dedicated, Perfect Month, and The Comeback as repeatable; Perfect Day, Milestone Maker, and Goal Crusher are one-time. The new migration changes Dedicated to one-time while retaining every historical occurrence and reversal. Perfect Day, Milestone Maker, and Goal Crusher still require a separate forward-only cadence migration before the requested taxonomy is complete. Do not enable the progression UI until all cadence rules have been aligned and verified. Badge unlock events themselves award no XP. XP is shown separately from achievement occurrence counts.

Wins derives current valid unlocks by pairing each revocation with the exact unlock event it reverses. Repeatable counts exclude reversed events and deduplicate by event identity; one-time achievements display at most one active unlock while retaining every audit event in history. Cards, recent unlocks, and details use the same server state. Offline provisional XP does not unlock badges; it remains labeled pending until confirmed by synchronization.

Two repeatable, non-XP achievements were added by forward-only migration `20261104002300_add_perfect_month_and_comeback_achievements.sql`:

- **Perfect Month** is earned once per completed calendar month in the workspace time zone. Every required opportunity must qualify, and there must be at least 12 distinct dates with required activity. Standard Mode holidays and rest days are neutral; Strict Mode dates are required. Historical months before the rule cutover are not newly awarded. A deterministic month key and account-level lock prevent duplicates.
- **The Comeback** is earned after a qualifying tracker opportunity, a past required opportunity with no saved outcome, and then seven consecutive qualifying eligible opportunities. A saved skip or nonqualifying outcome breaks a run but is not itself a “missed” trigger. Standard Mode excludes holidays and legitimate rest days from the opportunity sequence. Strict Mode treats each date inside the tracker period, including holidays and rest days, as required. Each recovery episode has a deterministic source key; repeat evaluations do not duplicate the award. Current schedule history is used conservatively, and unsupported pre-cutover history is not reconstructed.

The new achievement event source table is private, has RLS enabled, and grants no API-role access. It stores only the tracker association needed for safe correction and deletion reconciliation. Public achievement references carry dates and generic rule text, not tracker identifiers, names, entry IDs, notes, or metrics. Keep My Wins preserves the unlock and earned date while tracker deletion cascades the private source link. Delete Tracker and Wins revokes tracker-attributable Comeback events and revokes Perfect Month or Perfect Week only when the remaining eligible tracker set no longer qualifies. Achievement awards themselves grant no XP.

Forward-only migration `20261105000100_unify_progression_period_rules.sql` makes one server-side account-day evaluator authoritative for Perfect Day XP, the Perfect Day badge, All Trackers streaks, and period badges. It distinguishes perfect, failed, pending, neutral, future, and unsupported dates. A Perfect Day needs at least one required tracker and every required tracker to qualify. Standard Mode holidays and rest days are neutral; Strict Mode requires every active-period date. A saved skip is a failed required opportunity, not a completion. The still-open current day remains pending unless a known required failure has already occurred. All Trackers streaks count consecutive account-level Perfect Days and remain separate from individual tracker streaks. Neutral and pending days preserve the confirmed run; a known failed required opportunity resets it. No eligible trackers means neutral.

Under the same migration, **Perfect Week** is repeatable for each completed Monday-to-Sunday workspace week where all required opportunities qualify and at least three distinct dates have required activity. **Perfect Month** is repeatable for each completed calendar month where all required opportunities qualify and at least 12 distinct dates have required activity. Standard Mode holidays and rest days are neutral; Strict Mode dates remain required. Month and week awards use deterministic period keys and account locks, award no XP, and are reconciled after eligible history corrections or Delete Tracker and Wins. The new policy begins after its recorded complete-period cutovers; prior history is not backfilled under changed rules.

Consistency remains an average of daily adherence across the latest 30 completed eligible dates before the open current day. Daily adherence equals qualifying eligible trackers divided by eligible trackers. Standard Mode holidays and rest days are excluded; Strict Mode dates in the active period are required. Skips and unqualified saved outcomes count as uncompleted required opportunities. If there are no eligible dates, the UI shows no score rather than an invented zero. This is separate from Perfect Week and Perfect Month, which require every required opportunity to qualify.

The reusable client data repository is in `src/services/supabase/progressionRepository.ts`. It exposes confirmed and provisional XP, level and next-level progress, paginated score history, streak/milestone history, consistency, earned/locked badges, achievement progress/history, newly confirmed rewards, Perfect Day state, weekly progress, and a change subscription. UI code should consume these functions rather than duplicate scoring rules. The Achievements route keeps its established view unless the build explicitly sets `VITE_ENABLE_PROGRESSION_UI=true`. The variable is wired through GitHub Pages and remains unset/false by default; do not enable it until the target-environment migration and security checks below are complete.

## Tracker lifecycle and progression deletion limit

Active trackers alone participate in Today, current streak counts, and current actionable statistics. Archived trackers remain available to historical reports and Wins, where they are labeled as historical and do not appear as current streaks. Bin trackers are hidden from ordinary activity and reporting while their saved data, prior status, and XP remain recoverable during the 30-day window. Restoration retains the pre-Bin active or archived status. The client uses centralized lifecycle selectors in `src/domain/trackers/lifecycle.ts` for these distinctions.

Permanent tracker deletion now requires an explicit Wins choice. **Keep my Wins history** removes the tracker, entries, notes, and related sync receipts while preserving the authoritative XP ledger. Forward-only migration `20261104002200_preserve_deleted_tracker_reward_context.sql` snapshots only the original recorded tracker display name, server-defined reward reason, date/time, and XP amount for source-linked score and achievement events. The snapshot has no tracker, entry, score-event, or achievement-event foreign key and contains no notes, metrics, or tracker identifiers. Older generic source labels are shown as “Tracker name unavailable”; the current tracker name is never substituted for a historical one. Shared account-level rewards without a tracker source remain shared and are not attributed to a deleted tracker. The existing source anonymization and account-level achievement markers remain in place, and deleted activity cannot generate future rewards. Users are told before confirmation that tracker names and reward reasons remain in Wins. Automatic cleanup uses this same Keep Wins policy when the protected scheduler is enabled, but its database switch remains off unless separately activated.

**Delete tracker and its Wins history** reverses only exact tracker-linked check-in awards. It is available only when the account's progression ledger contains daily check-in awards and their reversals, every award has a matching tracker/source and award-state record, there are no reconstructed opening balances, shared or goal rewards, achievement events, or positive unattributed awards. If any of those conditions is present, the RPC raises a clear `55000` error before inserting the deletion ledger or removing tracker data. The frontend leaves the tracker in the Bin and reports the server reason. This intentionally conservative limit avoids guessing XP shares or revoking achievements without dependable historical dependencies. Stale zero-balance award-state rows are safe to anonymize; positive rows without a retained entry still block Delete Wins. Both modes run atomically under the per-tracker advisory lock and use the durable deletion ledger for idempotent retries.

## Security and activation

Private progression state uses row-level security and is not directly accessible to API roles. Users can read only their own ledger events; clients have no event write grants. Scoring routines run as `SECURITY DEFINER`, set an empty `search_path`, use schema-qualified references, and revoke direct execution from API roles. Ownership is derived from accepted database rows. The SQL suite verifies owner-scoped reads, rejection of direct authoritative ledger writes and forged achievement unlocks, tracker-source anonymization, account deletion, sync write validation, and revision conflict handling.

Do not show provisional values as official levels, ledger awards, badges, or celebrations.

## Safe migration and backfill rollout

Migrations `20261103000200` and `20261104000100` install schema and routines only. They no longer initialize all accounts during deployment or take shared locks on tracker tables. No existing account is initialized until an operator runs the bounded batch function. Migration `20261104000800` adds the resumable batch, `20261104001300` replaces its initializer with a set-based eligibility snapshot to avoid per-day settings, timezone, and holiday lookups, and `20261104001400` marks only qualifying same-day entries as represented in the opening balance. A skipped or incomplete entry can therefore become a new qualifying completion after cutover. The initializer evaluates one account per transaction under a per-account advisory lock; batches default to five accounts and reject sizes above ten. The batch function is owner-only and unavailable to API roles.

The cutover boundary is the initializer transaction's statement timestamp. Entries whose server-maintained change time precedes that boundary can contribute to the one estimated opening balance. A newly accepted write initializes first, then scores after cutover. Existing same-day qualifying entries are marked in award state without event creation. Awards for activity dated before the cutover calendar day are not newly generated, including delayed offline uploads. Reversals of already active awards remain allowed. This conservative rule avoids double counting when immutable prior schedule and device-balance records do not exist. Incomplete or absent server history is shown as unavailable; no zero balance or individual historic reward is fabricated.

For a fresh populated database, apply all migrations in timestamp order from `20261103000100` through the latest progression migration. For an existing database, inspect `supabase_migrations.schema_migrations` and apply only missing versions in order. Migrations `20261104001600_tracker_deletion_wins_retention.sql` through `20261104002100_reconcile_delete_wins_progression.sql` add the explicit retention mode, exact reversals for fully attributable accounts, safe handling of zero-value orphan state, idempotent retries, achievement preservation, and deletion reconciliation. Migration `20261104002200_preserve_deleted_tracker_reward_context.sql` must follow 02100; it is additive and forward-only. Its trigger captures display context before the existing anonymization triggers run. Never replay or rewrite a migration version already recorded by the target database. Hosted application, cleanup activation, and frontend production activation were not performed as part of this work.

The new context snapshot is written in the same transaction as the permanent deletion, so a failed deletion rolls it back. It stores only recorded tracker display name, reason code, reward date/time, and XP amount. Previously deleted trackers cannot be backfilled because the old anonymization deliberately removed their source names and links; those older score rows remain generic, and an achievement without a reliable original source remains without a tracker label. The 02200 migration must be applied before deploying the history UI that reads the new table. The migration and updated tests still require execution against an isolated disposable database with the full 02100 baseline before hosted rollout; do not reset an existing local database to test it.

The populated fixture preserved its authenticated user, active and archived trackers, goal tracker, and all 18 historical entries through migration. No account or achievement state was created by applying schema migrations. Batch initialization was idempotent and produced one opening event with the approved label. A 160-account synthetic benchmark contained 570 trackers and 145,850 entries across 30-, 180-, and 365-day histories. On the local arm64 Docker environment (PostgreSQL 17.11 container with no configured CPU or memory limits), fresh-account initializer timings after optimization were about 16 ms for 1 tracker × 30 days, 38 ms for 3 × 180 days, and 76 ms for 5 × 365 days. A separate large account completed in about 0.24 seconds. Earlier measurements before optimization took about 10 seconds for a medium account and 27 seconds for a large account. These are synthetic execution timings, not hosted hardware or production capacity guarantees.

Migration `20261105000200_make_dedicated_one_time.sql` changes only the server's Dedicated cadence definition and its current progress rows. It does not delete or rewrite achievement events, XP ledger rows, earned dates, or reversal records. Existing Dedicated tiers above one remain historical audit events; new qualification can create only the initial tier. This migration must follow `20261105000100_unify_progression_period_rules.sql`. Its changed database rule is backward-compatible with the existing read-only frontend shape, so apply the database migration before the frontend release. Keep progression UI disabled until the migration and the rest of the requested badge cadence changes have been verified.

For a hosted rollout, first inspect the project's applied migration versions and run a read-only preflight for Dedicated history and reversals. Save a logical database export outside the repository in access-controlled storage and verify that it can be restored into a disposable project; do not rely on paid point-in-time recovery being available. Apply only the missing migration through the normal migration pipeline, then verify that the migration version is recorded, RLS is unchanged, historical Dedicated event/reversal counts and XP ledger totals are unchanged, and a test account reaches tier 1 at 100 qualifying check-ins but receives no tier 2 at 200. Observe server errors and badge state before considering frontend activation. Stop if historical counts change unexpectedly or the migration fails; do not reset or edit migration history.

Start rollout with batch size 1. Observe sync/write latency and transaction duration in the target environment before increasing the batch size; stop on errors, visible write latency, or any batch exceeding the operator's maintenance threshold. The local implementation reads tracker/entry rows without taking shared table locks, but this run did not produce a trustworthy concurrent-write latency measurement. Keep historical backfill and frontend activation on separate release decisions.
